## 1. Executive summary

GeoLegalVault is a well-built prototype and an unusually honest one: the access-control core (Argon2id, pinned-alg JWT, refresh rotation with reuse detection, deny-by-default RBAC with a role × endpoint test matrix, server-side `$geoIntersects`, maker≠checker), the hash→anchor→verify loop, and the docs' candour about geofencing are real, tested, and worth keeping. It is **not yet a product you can sell**, and the distance is mostly *not* polish. Six things stop a first customer: **(1)** there is no way to change or reset a password, and no MFA; **(2)** every authenticated user can read and download every document regardless of its `classification`; **(3)** if an anchor transaction fails, is dropped, or the chain is reset, the document is stuck in `APPROVED` forever with no retry, no deployed worker, and an alert flag no API ever exposes; **(4)** a double-submitted amendment upload silently overwrites the stored bytes, so the version later gets approved, anchored, and permanently flagged `TAMPERED` with no way to clear it; **(5)** the headline "tamper-evident" verification degrades to a soft grey `NOT_ANCHORED` on a chain outage, a testnet reset, or an edit to one DB field, so "tamper-evident" is not accurate for those paths; and **(6)** backup covers MongoDB only, needs a host tool that isn't installed, has no restore script, and says nothing about the document bytes. Beneath those sit 18 High findings (lock-out-anyone DoS, a leaked RPC API key, 34 known-vulnerable runtime dependencies, non-atomic state transitions, a storage outage that freezes the whole API, no audit tamper-resistance, no deletion/retention story, no notifications/export/onboarding). My honest estimate: **roughly 3–4 engineer-months** to reach "first paying customer, supervised deployment" if the Blockers and the critical Highs are done in the order in §6, and materially more for a self-serve multi-customer product. The tamper-evidence core is sound enough that nothing needs to be redesigned — the gaps are state-machine atomicity, failure handling, and the missing account/ops/compliance layer around it.

**Counts:** 50 findings — **6 Blocker · 18 High · 21 Medium · 5 Low.**

**Status of the existing docs.** `PROJECT_ANALYSIS.md` is stale in three places (it says `CLAUDE.md` is empty, the login limiter is in-memory, and `faucet_check.py` is a stub — all fixed since). `THREAT_MODEL.md` has four claims the code does not support (rows 5, 7, 12, 16 — see SEC-02, SEC-18, SEC-12, CMP-01).

## 3. Detailed write-ups (every Blocker and High)

### SEC-01 — No password lifecycle, no MFA (Blocker)
**What's wrong.** `UserUpdate` has no password field and no endpoint changes one (OpenAPI paths in R20: only `/auth/login|refresh|logout`). The Settings page tells users to "ask an Administrator to reset your password" — but the admin can't either (D-001 lists it under "Not doing"). So every password is whatever an admin typed at creation, known to that admin, forever. There is no forced change on first login, no policy beyond length ≥ 8, no breached-password check, no MFA. For a legal/government buyer this fails basic procurement.
**Confirmed.** Code above plus the API surface listing; Settings text (`Settings.tsx:48`).
**Options.** (a) *Self-service change + admin-initiated one-time reset token (shown to the admin once, expires, forces change on first use)* — no email dependency, fits Guardrail #10. (b) *Email-link reset* — standard UX but needs an email provider (see FUN-01 / Guardrail tension G-5). (c) *SSO/OIDC (Entra/Okta)* — what enterprise buyers actually want; larger, and changes the auth model.
**Recommend (a) now, plan (c) next.** (a) closes the Blocker in ~1 week without new infrastructure: `POST /auth/change-password`, `must_change_password` flag set on admin-created/reset accounts, revoke the user's refresh families on change, add a minimum policy (length 12, deny top-N common passwords). Then TOTP MFA (stored secret + recovery codes) as a fast follow; SSO if a target customer demands it. Needs tests in the same change (Guardrail #11: RBAC-adjacent).

### SEC-02 — No document-level authorization (Blocker)
**What's wrong.** Authorization is role-only. R8: a TOP_SECRET document uploaded by one Legal Officer was read (`GET /documents/{id}` → 200) and given a download URL (`/download` → 200, geofence satisfied) by Authorized Staff, a different Reviewing Officer, the Auditor and the Administrator. `classification` is a free-text label never consulted; there is no owner/team/matter scoping, so a law firm cannot keep Client A's files from Client B's team, and a records office cannot compartmentalise. THREAT_MODEL row 5 ("every read/write re-checks the caller's permission") is true only of *role* permission.
**Confirmed.** R8; `grep -rn classification backend/app` shows no read-side use.
**Options.** (a) *Matter/workspace membership*: a `matters` (or "case") collection; documents belong to one; users get memberships; every document, version, anchor, verify and audit-by-target read filters by membership (Auditor/Admin get an explicit "all matters" flag). (b) *Classification levels vs user clearance* (numeric). (c) *Both*.
**Recommend (a).** Law firms and records offices think in matters/cases/registries, and (a) also gives the ethical-wall primitive. Make the filter a single dependency (like `require_geofence`) so no endpoint can forget it, and extend `test_authz_matrix.py` with a membership dimension. Biggest design change on this list: do it before building anything else on top of the document model (FUN-01/-03 depend on it). Check `docs/GeoLegalVault_Project_Plan.md` first (Guardrail #12) — if the plan excluded matter scoping, that is a recorded scope decision to reverse in DECISIONS.md.

### REL-01 — Anchor failure dead-ends (Blocker)
> **Status 2026-10-04: backend fixed (D-037..D-042, commit in the git log "REL-01").** Worker retry with idempotent chain-first reconcile, bounded backoff, heartbeat, opt-in compose service, permission-gated attention API and admin re-queue. UI alert and the CLAUDE.md #10 note are a second stage. The text below is the original finding, kept as the record.

**What's wrong.** `approve()` marks the version `APPROVED` and attempts anchoring up to 3×. After that, recovery relies entirely on `anchor_confirmer.py`, which (i) isn't in the Dockerfile, compose file, or DEPLOYMENT.md; (ii) only selects `status == PENDING` (`:29`), so any `FAILED` anchor (RPC down, gas/funds, revert) is never retried; (iii) polls a dropped `PENDING` tx forever and never sets the alert; (iv) has no `try/except` in `run_forever` (`:56-60`), so one RPC error kills it; (v) `anchor_pending_alert` is written (`service.py:287`) but `DocumentOut` doesn't include it, so neither UI nor API shows it; (vi) re-approving returns 409 (`ILLEGAL_TRANSITION`) because the doc is already `APPROVED`. Also, `promote_confirmed_anchor` marks the anchor `CONFIRMED` first (`workflow.py:182`) then updates version/doc in separate writes — a crash in between leaves a confirmed anchor on a non-ACTIVE doc that nothing picks up.
**Confirmed (R13, local Hardhat, isolated DB).** Automine off → approve returned `APPROVED/PENDING`; I killed the node and ran one worker pass → it **raised `ConnectionError`**; approving with the node down → 200 `FAILED` after 6.6 s, 3 FAILED rows, alert set; restarted the chain (= dropped tx / testnet reset) and ran the worker → both docs still `APPROVED` (one with `PENDING` and `alert=False`); re-approve → 409 for both.
**Options.** (a) *Worker v2*: loop catches/logs errors with backoff; retries `FAILED` anchors with capped attempts and exponential delay; **reconciles against the chain** (`getAnchor` for (doc, version): if it exists with the same hash, mark CONFIRMED instead of re-sending — this also fixes "tx broadcast but RPC errored → retry reverts"); re-submits `PENDING` txs older than N minutes (replace/speed-up, or new tx after reconciliation); makes `promote_confirmed_anchor` idempotent and resumable (a single conditional update per step, or pick up anchors that are CONFIRMED while doc isn't ACTIVE); raises the alert on stalls. (b) *Make anchoring synchronous-only with a user-visible retry button* — **violates Guardrail #3's letter** (no user-triggered anchor); see G-2. (c) *Move to a job collection polled by the same worker.*
**Recommend (a), deployed as the sanctioned single worker (Guardrail #10)**, plus: expose `anchor_pending_alert`/anchor state on `DocumentOut` and the Dashboard, add it to `/health` (chain-write readiness: balance > threshold, last successful anchor age), and add a reconciliation unit-test matrix (RPC down, revert, dropped, double-run). Add the worker to the Dockerfile/compose/Render docs.

### REL-03 — Duplicate amendment upload silently corrupts a version (Blocker)
**What's wrong.** `create_next_version` reads the latest version, computes `n+1`, **writes the object to `docs/{id}/v{n+1}`** (overwrite semantics), then inserts the version row. Two concurrent calls (double-click, client retry, two staff) both pick the same key; the second `put_object` overwrites the first's bytes, then one `insert_version` fails on the `(document_id, version_no)` unique index → HTTP 500. The surviving row's SHA-256 is for bytes that are no longer in storage.
**Confirmed end-to-end (R10).** Two parallel amend uploads → `[500, 201]`; V2 DB sha `fc5f9a…`, stored object sha `54583f…`; I then submitted, reviewed and approved it (all 200s, anchor CONFIRMED on-chain with `fc5f9a…`); Verify → **MISMATCH**, `integrity_flag=TAMPERED`, and no API path exists to clear the flag. The uploader's intended file is gone; the chain anchors a hash nobody can reproduce.
**Options.** (a) *Reserve first, then write:* insert the version row (status `UPLOADING`, unique index enforces `n+1`) → write object to a key that includes the version id or a random suffix → mark `DRAFT` only after the object write succeeds (`update_status` remains the only mutation, Guardrail #7 respected); delete the object on failure. (b) *Conditional PUT* (`If-None-Match: *`; supported by S3 and R2) so a second writer fails instead of overwriting, plus enabling bucket versioning. (c) *Idempotency key on the upload form* so a retry is a no-op.
**Recommend (a)+(b)+(c) together** — (a) fixes the race, (b) is a cheap belt-and-braces guard at the storage layer, (c) addresses the real-world trigger (retries). Add a concurrency test (same pattern as R10) in the same change (Guardrail #11). Also add an operator-only, audited way to clear a false `TAMPERED` flag (FUN-06) — as an admin action with a mandatory reason, not a silent edit.

### REL-04 — Verification degrades silently (Blocker)
**What's wrong.** `verify_version` converts any exception from the on-chain read into `{"exists": False}` (`:122-123`) and any non-existent anchor into `NOT_ANCHORED` (`:129-130`) — which the UI shows as neutral grey "NOT ANCHORED YET", writes `VERIFY_NOT_ANCHORED` to audit, and never flags. R12/R13: with the RPC down, a healthy anchored document verified as `NOT_ANCHORED`; after a chain reset (anchors gone) a document that is `ACTIVE`/`anchored: true` verified as `NOT_ANCHORED`; and with forged bytes + forged `sha256` + `version_no: 99` written directly to the DB, verify returned `NOT_ANCHORED`, no flag, no `VERIFY_FAIL` (while the two "simpler" tampers — swap the object; swap object + rewrite DB hash — were correctly `MISMATCH`/`TAMPERED`).
**Why it matters.** The product's stated guarantee is that DB and storage compromise can't produce a false pass. That holds for `VERIFIED`; but an attacker's *cheapest* goal is "not caught", and `NOT_ANCHORED` is not caught. "Tamper-evident" is therefore not accurate for these paths (CMP-04).
**Options.** (a) *Distinguish outcomes:* `VERIFIED`, `MISMATCH`, `NOT_ANCHORED` (only when the DB itself says never anchored), **`ANCHOR_MISSING`** (DB says anchored, chain says no → red, flag, audit), **`INCONCLUSIVE`** (chain/storage unreachable → amber, retry, never cached as a result row of a different kind). (b) *Chain-side reconciliation job:* periodically scan `AnchorCreated` events and compare against DB — catches the DB-edit case where the attacker also flips `anchored=false`. (c) *Derive the lookup key from the anchor row/tx receipt rather than the mutable version row.*
**Recommend (a) now (S–M), (b) in the same worker as REL-01 (the "blockchain confirmation polling" worker is the sanctioned place; reading event logs is the same job — note this as an interpretation in DECISIONS.md).** (c) is cheap once (a) exists. Update the UI copy and the Verification tests; change the API schema (additive enum values) deliberately.

**Update (D-049, backend; UI pending):** verify now returns `CHAIN_UNREACHABLE` (amber, no verdict, audited, never flagged) when the chain cannot be read, `ANCHOR_MISSING` / `FILE_MISSING` (flagged `UNCONFIRMED`, audited) when the database says anchored but the chain or the store says no, and keeps `NOT_ANCHORED` for versions the database does not claim were anchored. The on-chain read is bounded (`CHAIN_READ_TIMEOUT_SEC`, default 10 s, no retries; it previously could take 150+ s). D-025 clearing treats an unreachable chain as "unable to verify". **Still open under REL-04:** an attacker who also clears every "claims anchored" signal in the database still gets a grey `NOT_ANCHORED`; options (b) (event-log reconciliation) and (c) (chain-derived key) are deferred (see D-049 limits).

### OPS-01 — Backup/restore (Blocker)
**What's wrong.** Only MongoDB, and only via a host-installed `mongodump` (R20: `backup.sh` exit 1 on this machine). There is no restore script (just an echoed command), no backup of the R2/MinIO objects (the actual legal documents), no bucket versioning/object-lock/retention, no scheduled run, no restore drill. DEPLOYMENT.md:131 says "Atlas takes automatic snapshots on M0's backup policy" — I could not verify that offline and, to my knowledge, Atlas free (M0) clusters don't offer cloud backups; **check before relying on it**. The immutable-version design means a lost or overwritten blob is unrecoverable (only its hash survives on-chain). One more restore hazard: restoring an *older* DB snapshot while the chain already holds a later anchor for `(docId, v2)` means a new V2 upload reuses `docs/{id}/v2` (overwriting) and can never be re-anchored (`already anchored`).
**Confirmed.** R18: dump + restore of the audit DB round-trips (32 docs / 33 versions / 285 audit / 20 anchors identical) and the 3-way verify against the restored copy returns `VERIFIED` — so the *design* survives a same-point-in-time restore. R20 for the script exit code.
**Options.** (a) Enable bucket versioning + lifecycle retention on R2 (or nightly replicate to a second bucket/provider); Atlas M10+ (or self-managed + `mongodump --oplog`) with PITR; a documented, scripted restore + a post-restore `verify-all` command. (b) Quarterly restore drill as a runbook step. (c) Make object keys content-addressed/unique per upload (also fixes REL-03) so restores can't collide.
**Recommend (a)+(b)+(c).** A `scripts/restore.sh` and `scripts/verify_all.py` (read-only; iterates every ACTIVE version through the verify service and prints a summary) are small and double as a post-incident integrity check.

**Deployment-layer item carried in from step 2 (D-028, accepted by the owner 2026-10-04).** Slow-body (slowloris-style) protection is not handled by the app: the in-app size cap bounds bytes, not how slowly they arrive. Cover it at the edge/server when the deployment is specified: request-header and body read timeouts (gunicorn/uvicorn `--timeout-keep-alive`, `timeout`), and the reverse proxy / platform's body-timeout and `client_max_body_size`-style limit as defence in depth. Record the chosen values in `docs/DEPLOYMENT.md`.

**Update (D-033):** the oversize 413 used to carry `Connection: close`, which made uvicorn reset the connection so real clients could not read it; found only by real-HTTP smoke testing. The real-socket tests in `backend/tests/integration/test_body_limit_realsocket.py` now guard it (three of the six fail if the header returns). `scripts/smoke_starlette_upgrade.py` is the broader real-HTTP smoke check (auth cookie lifecycle, byte-exact upload/download, oversize and chunked bodies, one request per role) and is a candidate CI step once CI can start the full stack with the demo seed. The idle-client / trickling-client behaviour after a 413 (uvicorn keep-alive, 5 s idle) remains a deployment-layer setting.

### SEC-03 — Account lock-out as a DoS (High)
Per-email counter, not per-(email, IP) (`auth/service.py:125,140`). R1: six wrong guesses for `admin@…` → the real admin's correct password gets 429 for 60 s; an attacker looping once a minute keeps the admin out indefinitely. Unknown emails also create counter rows (TTL'd). **Options:** (a) progressive per-(email, IP) throttling with exponential delay, plus a higher account-level threshold that does *not* lock out a valid-password login from a known device; (b) CAPTCHA/proof-of-work after N failures; (c) admin unlock + alert on lock events. **Recommend (a)+(c):** keep the Mongo-backed atomic counter (it's good), key it by `(email, ip)` and add a coarser per-IP counter; never block a correct password solely on a counter an attacker can drive; audit `LOGIN_LOCKED`. Effort S.

### SEC-04 — No malware scan; shallow content validation (High)
R7: EICAR string accepted as `text/plain`; JS source accepted as `text/plain`; a zip with a 50 MB `evil.exe` accepted as `.docx` (51 KB on the wire, 50 MB inflated); a PDF with `/OpenAction /JavaScript` accepted. Correctly rejected: EXE-as-PDF, HTML-as-text, SVG-as-PNG, empty file, 11 MB and 200 MB bodies. **Options:** (a) ClamAV `clamd` scan on upload (best coverage; it's an extra daemon — see G-5); (b) managed scanning (R2/S3 event → vendor API, or a hosted AV API called from the upload path) — no new service in the deployment; (c) structural validation without AV: open the docx zip and require `[Content_Types].xml`/`word/document.xml`, cap uncompressed size and entry count (zip-bomb guard), reject macros (`vbaProject.bin`), parse the PDF and reject `/JavaScript`/`/Launch`/embedded files; restrict `text/plain` to a UTF-8 check. **Recommend (c) immediately (S), plus (b) before first customer, (a) if the customer hosts on-prem.** Quarantine status for scanned-pending files so nothing downloadable is unscanned. The existing "no AV" gap is documented; the validation gaps are not.

### SEC-05 — SPA refresh race forces logout (High)
`tryRefresh()` (`authToken.ts:45-52`) has no single-flight, and `api/http.ts` calls it from every concurrent 401. The Dashboard fires several queries at once, so when the 15-min token expires N requests each POST `/auth/refresh` with the same cookie. R3: six staggered refreshes → `[200, 200, 401, 401, 401, 401]` and then both fresh refresh tokens are 401 — the family was revoked by reuse detection. The server's reuse detection is correct; the client causes it. (Server-side, two truly simultaneous refreshes both succeed because `mark_replaced` isn't conditional — `auth/service.py:196,212` — a low-severity fork.) **Fix:** share one in-flight refresh promise in `tryRefresh`; make `mark_replaced` a conditional `find_one_and_update(replaced_by: None)` and treat a loss as reuse; add a vitest for http.ts (FE-01). Effort S.

### SEC-06 — Refresh cookie vs split-origin deployment (High; not browser-verified)
`SameSite=Strict; Secure; HttpOnly` (`auth/router.py:21-30`) is the right default for a same-site deployment. The documented target is Vercel (`*.vercel.app`) → Render (`*.onrender.com`): different registrable domains, so the SPA→API fetch is cross-site. Browsers won't set a `Strict` cookie from a cross-site response nor send it on a cross-site request, and third-party-cookie blocking compounds it → silent restore on page load fails and every session ends at 15 minutes. **Options:** (a) serve SPA and API under one registrable domain (`app.example.com` / `api.example.com`) — keep `Strict`/`Lax`; (b) proxy `/api` through the frontend host (Vercel rewrite) so the browser sees one origin; (c) `SameSite=None; Secure` + CSRF defence (weaker). **Recommend (a)** (also needed for any real customer domain/TLS story), with (b) as the fallback. I couldn't reproduce this without a real two-domain staging deploy — **do that before first customer**. Effort S plus infra.

### SEC-07 — RPC API key leaks through anchor error text (High)
R16 (repro with a fake key in the RPC URL path): `approve` → `FAILED`; the stored `error` is `HTTPConnectionPool(host=…, port=…): Max retries exceeded with url: /v2/SUPERSECRETKEY123 …`. That string is returned by `GET /blockchain/anchor/{version_id}` to **every `document:view` role** and copied into audit `meta` (visible to Auditors). Alchemy/Infura keys live in the URL path, so a real deployment leaks the provider key to all users. This is a Guardrail #2 spirit violation (secrets must not be logged/exposed) the existing checks wouldn't catch. **Fix:** store a sanitized, enumerated error (`RPC_UNREACHABLE`, `INSUFFICIENT_FUNDS`, `REVERTED`, …) in the anchor row/audit; keep raw text only in server logs after URL redaction; do not return `error` to non-admin roles. Rotate the Alchemy key that sits in the dev `.env` (and that I printed while reading it — see App. D). Effort S.

### SEC-08 — Known-vulnerable pinned dependencies (High)
`pip-audit -r requirements.txt --no-deps` (R20): 34 vulnerabilities — PyJWT 2.10.1 ×19 (fixes 2.12–2.15), python-multipart 0.0.20 ×12 (fixes 0.0.22–0.0.31), pytest 8.3.4 ×2 (dev). I did not read each advisory (several IDs post-date my knowledge) so I can't say which are exploitable in this configuration; the point is that two runtime packages sit directly on the auth and upload paths. `--no-deps` means transitive packages (starlette, urllib3, etc.) weren't audited. **Fix:** bump to the highest fixed versions, run the suite (8.5 min), add `pip-audit` and `npm audit --omit=dev` to CI, enable Dependabot/Renovate, and move to hashed lockfile (`pip-compile --generate-hashes`). Effort S.

### SEC-09 — Secrets lifecycle (High)
`JWT_SECRET` validation is "not a placeholder" only (`config.py:110`); `JWT_SECRET=x` passes in production. HS256 with one secret and no `kid` means rotation = invalidate all sessions at once. The service-wallet key is an environment variable on the host: no KMS/secret manager, no rotation procedure, and (BC-02) no contract-side path to rotate it. **Options:** (a) enforce ≥ 32 random bytes at startup; support two secrets (current+previous) with `kid` for graceful rotation; (b) move the wallet key to a managed signer (cloud KMS with secp256k1 signing, or a remote signer) so the process never holds raw key material; (c) document rotation runbooks (JWT, DB user, R2 token, RPC key, wallet) and test one. **Recommend (a) now (S), (b) with BC-02's owner/writer split (M), (c) alongside.** Guardrail #2 stays satisfied (key still only in env/secret store).

### REL-02 — Non-atomic transitions (High)
Every transition reads the document, checks `status`, then does unconditional `update_one({"_id": …})` (`documents/service.py:238-246`, `versions/service.py:86-92`). R9: four simultaneous approvals (two approvers) returned `[200, 200, 200, 409]`; DB shows 3 `APPROVE` audit rows, 7 anchor rows (1 CONFIRMED, 6 FAILED with `already anchored` reverts), 2 `ANCHOR_FAIL` audit rows for a document that **is** anchored, final status ACTIVE but `anchor_pending_alert: true` (the loser's alert write landed after the winner cleared it). R11: concurrent `approve` vs `changes_requested` reviews both returned 200, final state `DRAFT`, audit shows `CHANGES_REQ` then `REVIEW_PASS`; double `submit` → two `SUBMIT` audit rows. A UI double-click triggers the first scenario. **Options:** (a) compare-and-swap: `find_one_and_update({_id, status: expected}, {$set: …})` and treat no-match as `409 ILLEGAL_TRANSITION`, in `workflow.py` for every transition; (b) a per-document version counter (optimistic concurrency); (c) Mongo multi-document transactions (needs a replica set; Atlas has one). **Recommend (a)** — smallest change that closes it, and have `approve` claim the transition *before* it touches the chain. Add concurrency tests per transition (Guardrail #11: lifecycle state machine). Effort M.

### REL-05 — Blocking I/O freezes the API during a storage incident (High)
`storage.put_object/get_object` are synchronous boto3 calls inside `async def` handlers; boto3's default connect/read timeouts and retry policy turn a down storage endpoint into 25–30 s per call on the event loop. R14: with MinIO stopped, upload 29.1 s, verify 24.5 s, and a plain `GET /documents` issued meanwhile took 53.6 s. (web3 calls already use `asyncio.to_thread`; storage doesn't.) Also whole files are read into memory (≤ 10 MB cap makes this tolerable, but see SEC-14). **Fix:** run storage calls in `asyncio.to_thread`/`run_in_threadpool`, set explicit `Config(connect_timeout=3, read_timeout=15, retries={"max_attempts": 2})`, add a circuit breaker so repeated failures fail fast, and make `/health` report storage *write* readiness. Effort M.

### OPS-02 — An on-call engineer would not know (High)
(1) 5xx never appear in the structured request log — `JSONLoggingMiddleware` logs after `await call_next(...)` (`logging.py:29`), and an unhandled exception skips it (the server's stderr had uvicorn tracebacks for the 500s I provoked in R6 and zero `"status": 500` JSON lines), so the "alert on ≥500" comment in the file can never fire. (2) Module loggers (`logging.getLogger(__name__)`) aren't under the configured `geolegalvault` logger and the format is `%(message)s`, so `extra={email, ip, document_id}` is discarded: the log line is just `auth: login failed`. (3) `/health` returns `"status":"ok"` when only the chain is degraded (`main.py:68-75`) and checks nothing about wallet balance or anchor backlog. (4) Sentry is optional and `traces_sample_rate=0.0`. (5) No metrics, no dashboards, no alert rules; the one anti-stuck signal (`anchor_pending_alert`) is never exposed (REL-01). **Fix:** catch exceptions in the middleware and log with request id; one JSON formatter on the root logger that includes `extra`; a `/health/ready` covering Mongo, storage write, chain read, wallet balance, oldest PENDING anchor age; Sentry on in prod; 5 starter alerts (5xx rate, anchor backlog age, wallet balance, login-failure spike, health flapping). Effort M.

### FUN-01 — No notifications (High)
No endpoint, collection or UI for notifications (R20) even though SRS FR-21 promises an in-app list (and email was deliberately cut). A reviewer must poll the Dashboard; a submitter is told of `changes_requested` only if they open the document. **Options:** (a) in-app notification collection + bell + unread counts (no new service); (b) email via a transactional provider (called from the API process; failures retried by… see G-5); (c) both. **Recommend (a) first** — it fits the modular monolith and the plan's own MVP; add (b) with a Mongo outbox drained by the existing worker only after the Guardrail #10 question in G-5 is answered. Effort M.

### FUN-02 — Onboarding needs a script and DB credentials (High)
First admin = `python scripts/seed.py --email … --password …` run by someone with production Mongo credentials, with the password in shell history; `--demo` creates five users with a constant password in the repo (`seed.py:45`). No first-run wizard, no invite flow. **Options:** (a) one-time bootstrap token printed at first start (or env-provided bootstrap admin) that forces the password change from SEC-01 and then disables itself; (b) invite links (needs email); (c) keep the script but read the password from stdin/prompt and refuse `--demo` when `APP_ENV != development`. **Recommend (a)+(c)**; geofences and users are then created from the existing admin UI. Effort M.

### FUN-03 — Audit not usable as compliance evidence (High)
`GET /audit` has filters and a table but no export, and shows opaque ids because an Auditor has no `users:manage` (D-012). An Auditor can't hand a regulator a report or tell who "6abd…" is. **Options:** (a) CSV (and signed PDF) export honouring the current filters, with the filter set + generation timestamp + row hash in the header; (b) add actor display name/email into audit rows at write time (immutable snapshot — also helps after user changes) or a read-only `GET /audit/actors` for `audit:view`. **Recommend (a)+(b)-snapshot**, mindful of CMP-03 (don't snapshot more PII than needed). Effort M.

### CMP-01 — Audit log tamper-resistance (High)
Audit rows are inserted by the same app credentials that can also update/delete them (the append-only property exists only because no *route* does it — `audit/service.py:1-15`). No hash chain, nothing anchored. Entries are written *after* the state change (`workflow.py:89-99`), so a failed insert leaves an unaudited transition (and the user sees a 500 after the change committed). THREAT_MODEL row 16 ("append-only") overstates. **Options:** (a) separate least-privilege Mongo user for the app with `insert`/`find` only on `audit_logs` (no `update`/`remove`), enforced by DB roles; (b) hash-chain each row (`prev_hash` + canonical row hash); (c) periodically anchor the chain head on-chain; (d) write the audit row *before* the state change in one transaction (replica set). **Recommend (a)+(b) first** — meaningful tamper-evidence without chain changes; (c) only after G-8 is decided (it adds a new anchoring trigger, which Guardrail #3/#8 constrain); (d) with REL-02's atomicity work. Effort M.

### CMP-02 — Retention and deletion (High)
There is no deletion path: documents can only be archived (`ARCHIVED`, hidden); `retention_until` is a field that is always `None` (`service.py:154`) and read nowhere; `refresh_sessions`, `verification_records`, `audit_logs` have no TTL; a user's name can be edited but not their email, and users can't be deleted or anonymised. A GDPR-style erasure or a legal-retention expiry cannot be executed. **Options:** (a) *Retention policy engine*: per-doc-type retention date set at activation, enforced by an admin-visible "due for disposal" queue; (b) *Disposal = delete the blob + tombstone the document* while keeping the version row (hash, version_no, anchor) — arguably compatible with Guardrail #7 (the version's content/hash fields are never mutated; only the object is removed and `status` becomes a new whitelisted `DISPOSED`), and verification returns an explicit `DISPOSED` rather than a storage error; (c) *PII minimisation*: TTL on sessions/verification rows, anonymise user records on deactivation by policy. **Recommend (b)+(c) with (a) as the driver — but (b) needs your decision (see G-4).** Effort L.

### CMP-04 — Scope of the "tamper-evident" claim (High)
What is protected: the bytes of an *approved version*, via the on-chain hash (R12 cases 1–2 prove this). What is not: document status, who approved/when (audit is mutable, CMP-01), ownership, classification, version ordering, user/role assignments, geofence definitions, and — via REL-04 — whether verification even reaches the chain. A DB operator can rewrite approval history without detection. **Fix (S):** tighten every customer-facing statement to "the content of each approved version is tamper-evident"; state what is *not* covered; fix THREAT_MODEL rows 5/12/16; resolve REL-04. Whether to extend coverage (audit anchoring, metadata hashing) is a product decision tied to G-8.

### BC-01 — Testnet anchoring: what a customer must understand (High, business)
See §4 (G-1) and the plain-language statement below; the effort is a documentation/contract task, not code. (Write-ups appear in this order: the six Blockers, then the 18 Highs as they appear in the table.)
**What to tell a customer.** (1) *Permanence:* Sepolia is a *test* network. It has no economic security guarantee, the Ethereum ecosystem has retired testnets before (Ropsten, Rinkeby, Kovan and Goerli were shut down; Holesky was replaced by Hoodi), and a testnet can be reset or sunset on the maintainers' schedule — check the current published schedule for Sepolia before signing anything. If the network goes away, every on-chain anchor goes with it; the app's own `blockchain_anchors` rows (tx hash, block number) are a local copy, not an independent proof. (2) *Trust:* with one hot service key as writer, the chain proves "this key submitted this hash at this block time", not authorship or honesty of the uploader (THREAT_MODEL limitation 5). (3) *What a reset does today:* all versions verify as `NOT_ANCHORED` and affected docs need re-anchoring, for which there is no tooling (BC-02/REL-04). (4) *Value:* the product today is a **prototype-grade integrity audit trail**, not legal-grade timestamping.
**Realistic production options *if* Guardrail #8 were revisited** (your decision; I'm not recommending a switch): (i) Ethereum mainnet — strongest neutrality; cost per anchor tracks mainnet gas and, because Merkle batching is also out of scope (#8), scales linearly with approvals; (ii) an Ethereum L2 (Base/Optimism/Arbitrum or a ZK rollup) — orders of magnitude cheaper, inherits L1 security with a longer exit/finality story; (iii) a permissioned/consortium chain run by the customer + auditors (Besu/Fabric) — fits a government registry, customer carries ops; (iv) RFC 3161 qualified timestamping (eIDAS-qualified TSAs in the EU) — legally recognised in many jurisdictions with no chain at all, often what lawyers actually recognise; (v) dual: chain + TSA. Any of these also touches Guardrails #1/#3/#8 and needs a plan decision (#12).

### BC-02 — Contract/key model (High)
`DocumentAnchor` has one `owner` (= deployer = the hot service wallet), `writers[owner]=true`, `setWriter` owner-only, no `transferOwnership`, no pause (`DocumentAnchor.sol:10,43-46`). Consequences: (1) a stolen key lets the attacker anchor arbitrary hashes for any not-yet-anchored `(documentId, version)` — including **pre-anchoring future versions of existing document ids** (ids are visible to every viewer), after which the legitimate anchor reverts with `already anchored` forever (permanent poison; the app would see it as `FAILED`, REL-01); (2) the same key is the owner, so `setWriter(false)` can be called by the thief too and there is no way to move ownership to a safe key; (3) recovery = deploy a new contract, switch `CONTRACT_ADDRESS`, re-anchor every ACTIVE version (no tool; verification of old docs meanwhile = REL-04); (4) no on-chain way to supersede a mistaken anchor. Existing anchors can't be altered by a thief (good). **Options:** (a) split roles: owner = cold key/multisig (Safe), writer = hot service key; add `transferOwnership` (2-step); (b) add `anchor` idempotency (`same hash → no revert`) so a retry after a lost response is harmless; (c) a `reanchorTool` script + app support for a `contract_address` per anchor (the `blockchain_anchors` row already stores `contract_address`, so verification can follow it); (d) pause switch. All stay within Guardrails (#3 permits a second writer "deliberately and documented"; no proxy, no upgradeability, #8). **Recommend (a)+(b)+(c)** in a v2 contract deployed *before* the first customer's data exists; since the contract is non-upgradeable by design, this is far cheaper now than later. Needs Hardhat tests (Guardrail #11).

## Appendix B — Geofence headers: what an attacker with a valid account can and cannot do

*Facts from R4/R5 and code.* The four `X-Geo-*` values are fully client-chosen. The server validates ranges, rejects accuracy > 100 m (and NaN accuracy), rejects timestamps *older* than 60 s, and then decides inside/outside against the **user's own assigned, active fences** server-side.
**Can:** report any coordinates inside any fence assigned to them, from anywhere on earth (DevTools sensors, a script, `curl`); report accuracy 0; make one header set valid forever with a future/NaN/inf timestamp, or replay it (SEC-12); learn the shape of their assigned fences by probing — 200 vs 403 is a point-in-polygon oracle (~120 req/min per IP, bypassable with XFF, SEC-10); flood the audit log with denials carrying chosen lat/lng (SEC-11).
**Cannot:** use a fence not assigned to them; use an inactive fence; bypass RBAC or maker≠checker with location; get an `ALLOWED` decision from a client flag (none is read). Geofence evidence in the audit log should therefore be read as "the client claimed to be here", never "was here".
**Copy adequacy.** The wording is accurate and consistent with Guardrail #6, but it appears only on the Login footer, the Geofence Status page and the LocationGate; the Upload/Approve success states and the audit/verification views don't repeat it, and nothing tells a buyer that a geofence record is a *claim*. Before selling, put one sentence at each decision point and in the contract: "location is reported by the user's device and is a policy input, not proof of presence" (SEC-15).
